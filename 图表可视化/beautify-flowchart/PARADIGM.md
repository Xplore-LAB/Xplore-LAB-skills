# 范式提案：Constraint Chain（约束链）

> 从 beautify-flowchart 构建方法论中提炼出的 AI 执行范式，
> 与 ReAct / CoT / ToT 同级，面向不同的问题类别。

---

## 一、现有范式图谱

AI 推理与执行的范式，按问题类别分布：

| 范式 | 核心循环 | 解决的元问题 | 代表场景 |
|------|---------|-------------|---------|
| **Chain-of-Thought** (CoT) | Think → Think → Think → Answer | 复杂推理需要中间步骤 | 数学、逻辑、规划 |
| **ReAct** (Reason+Act) | Reason → Act → Observe → Reason... | 推理和行动需要交错进行 | 工具调用、网页搜索、代码调试 |
| **Tree-of-Thoughts** (ToT) | Branch → Evaluate → Prune → Branch... | 单条推理链容易陷入局部最优 | 创意写作、策略规划 |
| **Constraint Chain** (CoC) | Extract → Confirm → Constrain → Route → Execute → Verify | **生成任务中，对源头的忠实度和对约束的遵守度无法通过"多想一想"来保证** | 设计稿还原、文档重构、图表美化、翻译、代码迁移 |

---

## 二、ReAct 的边界：为什么"多想一步"不够

ReAct 的核心是 **Reason 和 Act 交错**——每做一步，观察结果，再推理下一步。这在以下场景表现出色：

- 网页搜索：搜 → 看结果 → 不够 → 换个词搜
- 代码调试：写 → 跑 → 报错 → 改 → 再跑

但有一类任务，ReAct 是错的。这类任务的共同特征是：

1. **存在一个必须忠实还原的"源头"**（原图、原文、原始设计）
2. **用户有硬约束，违反任何一条就是失败**（"布局别动"）
3. **表面上相似的请求对应根本不同的执行路径**（"美化一下" vs "给我可编辑的"）
4. **AI 的"善意多做一点"恰好是用户最反感的行为**

在这类任务上，ReAct 的观察-修正循环会产生一个致命问题：

```
AI: 我把布局也优化了一下
用户: 我说了布局别动
AI: 好的我改回来
用户: 这已经不是原图的布局了
AI: 让我再调整一下...
用户: 算了，我自己画吧
```

**ReAct 的观察-修正循环在这里失效了，因为错误不是"不够好"，而是"越改越远"。** 每次修正都在原错误上叠加新的偏离，因为 AI 缺乏"回到源头"的机制。

## 三、Constraint Chain（约束链）—— 新范式

### 3.1 定义

> **Constraint Chain（约束链）是一种 AI 执行范式，要求在生成任何输出之前，先完成三个不可跳过的前置步骤：提取源头 → 与用户确认 → 形式化约束，然后根据约束选择互斥的执行路线，最后用客观检查清单验证。**

### 3.2 六环链

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ Extract  │───→│ Confirm  │───→│Constrain │───→│  Route   │───→│ Execute  │───→│  Verify  │
│  提取     │    │  确认     │    │  约束     │    │  路由     │    │  执行     │    │  验证     │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
     │               │               │               │               │               │
     │               │               │               │               │               │
     ▼               ▼               ▼               ▼               ▼               ▼
 从源头提取      不确认不前进    约束是硬边界    相似请求→      只执行已批准    客观 yes/no
 7 个维度的      不确定项必须    约束覆盖范围    不同路线       的方案          逐项检查
 结构化信息      显式标记        大于模式选择    路线互斥        不擅自发挥      不通过就返回
```

### 3.3 与 ReAct 的本质区别

| 维度 | ReAct | Constraint Chain |
|------|-------|-----------------|
| **推理-行动关系** | 交错进行，观察驱动修正 | 前置全部推理，锁定后一次性执行 |
| **错误修正方式** | Observe → 发现问题 → 调整下一步 | 执行前锁定约束 → 执行后清单验证 → 不通过则重新执行 |
| **对源头的态度** | 没有"源头"概念，每次观察都是新输入 | 提取的源头是锚点，不可偏离 |
| **约束的地位** | 约束是 prompt 里的"尽量" | 约束是硬规则，冲突时强制改变执行模式 |
| **何时终止** | 观察结果满意 | 所有检查项通过 |
| **核心风险** | 越修越远（修正循环发散） | 前置确认耗时（但避免了返工） |

### 3.4 约束链的链式传递特性

约束链的核心洞察：**约束在链上单向传递，每一环的输出缩小下一环的搜索空间。**

```
Extract:    "图中有 12 个节点，3 个判断，2 个泳道"
               │ 缩小空间：只有这 12 个节点需要处理
               ▼
Confirm:    "节点 3 的文字大概率是'审批通过'，无法确认节点 7 的文字"
               │ 缩小空间：确认的锁定，不确定的标记
               ▼
Constrain:  "布局完全一致 + 文字完全一致"
               │ 缩小空间：只能改颜色/字体/线宽
               ▼
Route:      "路线 A：图片美化，模式 style"
               │ 缩小空间：排除了重建和布局调整
               ▼
Execute:    "只修改 12 个节点的颜色和字体"
               │ 执行空间已被约束到最小
               ▼
Verify:     "布局没变？✓  箭头一致？✓  分区保留？✓"
```

**这就是"约束链"的核心机制：不是让 AI 在巨大的可能性空间中"选择更好的"，而是通过链式约束把空间缩小到"只能做对的"。**

## 四、约束链的三个子机制

### 4.1 锚定机制（Anchoring）

> 执行前必须从源头提取结构化信息，作为后续所有操作的锚点。

为什么需要它：AI 的默认行为是从 prompt 直接跳到执行。在美化流程图中，这导致 AI 看到图就开始画，而不先理解图里有什么。ReAct 允许 AI 边观察边调整，但如果第一步就理解错了（比如看错了某个节点的文字），后续修正都是在这个错误上的叠加。

约束链的解法：强制第一步只做提取——结构化地、穷尽地、带不确定性标记地提取。提取完成前禁止进入执行。

### 4.2 硬约束机制（Hard Constraining）

> 用户约束不是"尽量"，而是硬规则。约束与模式冲突时，模式必须降级。

为什么需要它：AI 倾向于把约束当建议。在 ReAct 模式下，"保持布局大致不变"会被 AI 理解为"你可以稍微调一下对齐"。用户说"别动布局"，AI 理解为"我动一点点应该不会被发现"。

约束链的解法：定义模式 = {允许操作, 禁止操作}。用户约束可以收窄允许集合，但绝不能放宽。冲突时约束优先，模式必须降级。

```
模式 smart：允许 {颜色, 字体, 线宽, 位置, 对齐, 间距, 连线绕行}
用户约束："布局完全一致"
    → 允许 ∩ 禁止(动位置) ∩ 禁止(动连线绕行)
    → 剩余允许 {颜色, 字体, 线宽}
    → 这不等于任何模式
    → 强制降级为 style（最接近的允许集合）
```

### 4.3 分叉路由机制（Bifurcated Routing）

> 表面相似的请求必须被路由到互斥的执行管线，不能混做。

为什么需要它：ReAct 的交替推理假设"做错了可以观察然后修正"。但"给我美化图片"和"给我可编辑源文件"不是"做得够不够好"的问题——是根本目标不同。给错了类型就是完全失败，修正意味着从头重做。

约束链的解法：在提取和约束之后，强制做一次路由判断。两个路线互斥，有不同的验收标准。选错了路线，Verify 环节会发现并触发重做——但至少不会混做。

## 五、适用域

Constraint Chain 不适合所有任务。它适用于满足以下条件的问题类别：

### 适用条件（四个"是"）

1. **有源** — 存在一个必须忠实还原的参考源（图、文、代码、设计稿）
2. **有界** — 用户有明确的、可形式化的约束条件
3. **有叉** — 相似请求对应不同执行路径，走错路径的代价是重做
4. **有尺** — 存在客观的、yes/no 的验收标准

### 适用场景举例

| 场景 | 源头 | 硬约束 | 分叉 | 验收标准 |
|------|------|--------|------|---------|
| 流程图美化 | 截图/手绘 | 布局不动/文字不变 | 美化 vs 重建 | 布局/箭头/分区/遮挡 |
| UI 设计稿还原 | 设计稿截图 | 像素级一致 | 静态还原 vs 可交互 | 间距/颜色/字体/交互 |
| 文档格式迁移 | 原始文档 | 内容不变/结构保留 | 纯格式 vs 可编辑 | 内容完整性/结构对应 |
| 代码翻译 | 源代码 | 行为等价 | 直译 vs 惯用改写 | 测试通过/行为一致 |
| 数据可视化 | 数据表/描述 | 数据准确 | 静态图 vs 交互式 | 数据点/比例/标注 |
| 图表重构 | 手绘草图 | 数据不变 | 快速草图 vs 出版级 | 数据准确性/可读性 |

### 不适用场景

- 开放式创意（没有"源头"）
- 探索性研究（没有明确的验收标准）
- 简单问答（没有分叉路由的必要）
- 对话式交互（用户的反馈本身就是观察-修正循环）

## 六、与现有范式的互补关系

```
                    │  需要交错观察修正？
                    │
          ┌─────────┴─────────┐
          │ YES               │ NO
          │                   │
          ▼                   ▼
    需要探索多条路径？    有明确的源头和约束？
          │                   │
    ┌─────┴─────┐       ┌─────┴─────┐
    │ YES       │ NO    │ YES       │ NO
    ▼           ▼       ▼           ▼
  Tree-of-   ReAct   Constraint   Chain-of-
  Thoughts           Chain        Thought
```

**四种范式不是竞争关系，是互补关系。** 同一个复杂任务可能在不同阶段使用不同范式：

```
设计稿还原任务：
  ├─ 理解设计意图 → CoT（推理设计决策）
  ├─ 提取设计规范 → CoC（提取→确认→约束→路由）
  ├─ 实现具体组件 → ReAct（写→跑→调）
  └─ 验收 → CoC（逐项检查）
```

---

## 七、与 ReAct 的"境界"对应

如果说 ReAct 代表的是 **"知行合一"** 的境界——知和行交替推进，互为印证——

那么 Constraint Chain 代表的是 **"先见后行"** 的境界——在动手之前，先穷尽观察，先划定边界，再在一个被约束到最小的空间中，一次性把事情做对。

这不是比 ReAct "更高"的境界，而是不同问题类别需要的不同境界。ReAct 是"边做边看"，Constraint Chain 是"看好再做"。用错了境界，就会陷入 v1.1 的困境——AI 在 ReAct 式的修正循环中越改越远，因为每次修正都在偏离源头。

## 八、命名备忘录

| 名称 | 缩写 | 优点 | 缺点 |
|------|------|------|------|
| **Constraint Chain** | CoC | 与 CoT 命名风格一致，强调链式传递 | 不够直观 |
| **Extract-then-Execute** | EtE | 直指核心动作 | 没体现约束 |
| **Anchor & Bound** | A&B | 形象（锚定+定界） | 不够学术 |
| **Contract-First Generation** | CFG | 突出契约精神 | 太长 |
| **约束链** | — | 中文直观 | 英文翻译不够 catchy |

**推荐：Constraint Chain（约束链）**，原因：
- 与 CoT（Chain-of-Thought）形成姊妹范式
- "Chain"体现了约束在链上单向传递的核心机制
- 容易扩展：Constrained CoT、Constraint-Chain-of-Thoughts
