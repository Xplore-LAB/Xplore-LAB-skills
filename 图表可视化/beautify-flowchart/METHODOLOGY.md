# beautify-flowchart 构建方法论

> 从 v1.0 到 v2.2 的演进中提炼出的 Skill 设计原则、架构模式和可复用方法论。

---

## 一、核心设计哲学

### 1.1 "先提取，再执行" —— 方法论优先于启发式

**问题**：v1.x 的 AI 拿到一张流程图后直接开始"美化"，经常改变布局、误读文字、输出用户不想要的东西。

**解法**：强制执行六步固定流程。在任何绘制/美化动作之前，必须先完成提取和确认。

```
提取 → 确认 → 约束 → 路线 → 模式 → 执行
  │       │       │       │       │       │
  │       │       │       │       │       └── 只在最后一步才动手
  │       │       │       │       │
  │       │       │       │       └── 选定后就锁定，不中途切换
  │       │       │       │
  │       │       │       └── 两条路互斥：美化 or 重建
  │       │       │
  │       │       └── 从用户话里提取硬约束
  │       │
  │       └── 给用户看，尤其标注不确定项
  │
  └── 七个维度全量提取，不遗漏
```

**核心洞察**：AI 擅长执行，但不擅长判断"该不该执行"。用一个固定的分析框架把"该不该"变成 checklist，AI 只需照做，不需要判断是否需要做。

---

### 1.2 任务分叉 —— 相似的请求，根本不同的目标

用户说"帮我处理一下这张流程图"，实际可能是两个完全不同的需求：

| 用户真实目标 | 对应路线 | 错误做法 |
|-------------|---------|---------|
| 图片好看点，截图用 | 路线 A：图片美化 | 重建了一个 draw.io，用户说"我只是想调个色" |
| 后面还要改字改结构 | 路线 B：可编辑重建 | 给了一张美化后的 PNG，用户说"我要能双击改字啊" |

**设计决策**：把两类任务定义为互斥路线，skill 必须先判断走哪条。这不是"两种模式"——是两条完全不同的执行路径，连验收标准都不一样。

**判断依据**：
- 用户说"美化"/"布局别动"/只要图片 → 路线 A
- 用户说"可编辑"/"后面还要改"/要源文件 → 路线 B

---

### 1.3 "诚实优于完美" —— 不确定性标记系统

图片中的文字可能模糊、遮挡、太小。AI 容易自信地"脑补"。

**三级标记系统**：
- **可确认**：文字清晰，100% 确定
- **大概率如此**：有线索但不完全确定
- **无法确认**：看不清，不猜测

**设计意图**：把 AI 的"我猜这是 X"变成"大概率是 X，需要你确认"。这是一个谦逊机制——承认不确定性比提供错误信息更好。

## 二、架构模式

### 2.1 约束驱动的行为降级

用户约束不是"建议"，是"硬规则"。关键设计：**约束可以强制改变执行模式**。

```
用户说"布局完全一致"
    │
    ├─ smart 模式 → 强制降级为 style
    ├─ both 模式 → 降级为 style
    └─ layout 模式 → 不可用（会改布局）
```

**设计原理**：与其让 AI "尽量保持布局"，不如直接切换到"只允许改样式"的模式。模式定义了允许和禁止操作的边界，约束可以收窄这个边界，但不能放宽。

**可泛化模式**：
```
模式 = {允许操作集合, 禁止操作集合}
约束 = 对允许/禁止集合的进一步限制
最终行为 = 模式 ∩ 约束
```

---

### 2.2 中间表示层 —— JSON 作为真相源

**问题**：直接把流程图逻辑写到渲染脚本里，导致逻辑和渲染耦合，改一个就要改另一个。

**解法**：引入声明式 JSON 中间层。

```
语义图 ──→ JSON 规范 ──→ 渲染器 ──→ .vsdx / .drawio / SVG
  │            │              │
  │            │              └── 可替换：COM / pywin32 / mermaid-cli
  │            │
  │            └── 单一真相源，不依赖具体渲染器
  │
  └── 平台无关的流程描述
```

**关键属性**：
- JSON 包含节点（id/text/shape/x/y/w/h/style)、连接器（from/to/text/route)、布局元数据
- 渲染器从 JSON 生成，不包含业务逻辑
- 同一个 JSON 可以渲染到不同格式
- JSON 可被版本控制、可被 diff、可被人工审查

**可泛化模式**：任何需要"描述 → 生成"的 skill 都可以用这个三层架构。

---

### 2.3 分层契约 —— Layout Contract 模式

直接渲染一个松散的图 → 连接线缠绕、节点不对齐、阅读顺序混乱。

**Layout Contract 五层管线**：

```
semantic_graph  →  验证流程逻辑（节点类型、边规则、反馈回路）
     │
layout_contract →  固定分区、坐标、连接器通道、排版
     │
style_contract  →  选择字体、颜色、线宽、节点样式
     │
render          →  只执行，不做决策
     │
qa_pass         →  检查交叠、碰撞、标签、逻辑一致性
```

**每层只做一件事**：
- 逻辑层不关心颜色
- 布局层不关心逻辑
- 样式层不关心坐标
- 渲染层不做判断
- QA 层不修改内容

**核心规则**：在渲染前修正布局契约，而不是渲染后在像素层面修补。

---

### 2.4 渐进式知识加载 —— 主文件 + 参考文件

SKILL.md 是主指令，但它不包含所有细节。深层知识放在 `references/` 目录下，由 skill 指令告诉 AI "什么时候去读哪个文件"。

```
SKILL.md                    # 总控：流程、规则、禁止事项
  │
  ├─ 当用户要 Visio 时 → references/visio-automation.md
  ├─ 当用户要出版级图 → references/editorial-diagram-style.md
  ├─ 当图有复杂分支时 → references/logic-validation.md
  └─ 当用户要精修 Visio → references/visio-layout-contract.md
```

**设计原理**：skill 的 prompt 是有限的上下文窗口。把"什么时候需要什么知识"的逻辑写在主文件里，具体知识放在参考文件里，AI 按需加载。这避免了主文件过于庞大，也避免了每次加载不需要的知识。

## 三、质量保障体系

### 3.1 "禁止事项"与"允许事项"同等重要

大多数 skill 只告诉 AI 要做什么。这个 skill 用了同等篇幅告诉 AI **不做什么**。

```
style 模式下禁止：
├─ 重新布局
├─ 擅自拉开节点间距
├─ 改变箭头走向
└─ 改变阅读顺序

可编辑重建时禁止：
├─ 把"重建"伪装成"修图"
├─ 未说明误差就声称"完全一致"
└─ 在文字不清时擅自编造业务文案
```

**设计原理**：AI 的默认行为是"多做一点"——多调一下布局、多润色一下文字。但这些"善意"的额外操作恰好是用户最反感的。把禁止事项写清楚比把允许事项写清楚更重要。

**来源**：这些禁止项全部来自真实的失败案例——AI 在 style 模式下重排了布局、在重建时编造了看不清的文字。

---

### 3.2 两级验收标准

**图片美化结果**：
- 布局是否没变（style 模式下）
- 箭头关系是否一致
- 分区是否保留
- 颜色语义是否一致
- 是否有错位、遮挡、重叠

**可编辑重建结果**：
- 文件是否能正常打开
- 所有框是否可编辑
- 文本是否可双击修改
- 连线是否可单独拖动
- 结构是否与原图一致

**设计原理**：验收标准是客观的、可检查的、不需要主观判断的。每一条都是 yes/no 问题。

---

### 3.3 质量关口 —— "先可用，再好看"

```
第一版标准（必须满足）：
├─ 所有节点对齐到可见网格
├─ 所有主路径连接器正交
├─ 无连接线穿过节点
├─ 无连接器标签与节点、线、区域标题重叠
├─ 反馈回路走主路径外侧
├─ 判断节点的分支都有标签
├─ 字体和字号一致
└─ 读者能在 3 秒内追踪主路径

只有以上全部通过，才允许添加颜色、图标、阴影、装饰。
```

**设计原理**：AI 喜欢先做视觉美化（因为效果立即可见），但结构问题在美化后更难发现和修复。强制"结构先行"避免了在错误基础上叠加装饰。

---

### 3.4 逻辑验证 —— 两层验证

```
渲染前验证（语义层）：
├─ 一句话描述图的主要主张
├─ 列出所有节点的语义顺序
├─ 标记哪些是替代方案、哪些是顺序步骤
├─ 标记中间产物 vs 最终交付物
├─ 检查所有判断节点都有标记出口
└─ 检查所有反馈回路回到可修复的步骤

渲染后验证（视觉层）：
├─ 追踪主路径从入口到输出
├─ 追踪每个分支，确认到达输出或反馈回路
├─ 确认可选输出在视觉上次要
├─ 确认颜色不暗示虚假含义
└─ 确认可以口头解释图而不与箭头矛盾
```

**核心见解**：不要只验证图片，验证图片背后的流程模型。视觉上好看的图可能在逻辑上是错误的。

## 四、从 v1 到 v2 的演进教训

### 4.1 版本演化路径

| 版本 | 定位 | 核心机制 | 问题 |
|------|------|---------|------|
| v1.0 | 单一美化工具 | 基础 mermaid 渲染 | 太简单，无差异化 |
| v1.1 | 多模式选择器 | 4 种模式 + 6 种主题 + 参数 | 用户不知道该选什么，AI 乱选 |
| v2.0 | 方法论框架 | 强制 6 步流程 + 任务分叉 | — |
| v2.1 | + Visio 集成 | JSON 规范 + COM 自动化 + 质量模式 | — |
| v2.2 | 文档同步 | frontmatter + CHANGELOG 补全 | — |

### 4.2 关键转折点：从"特征表面"到"深层结构"

v1.1 的思维模式：**给用户更多选择 → 更好的结果**
- 4 种模式、6 种主题、5 种方向、4 种缩放……参数爆炸
- 用户不知道选什么，AI 也不知道
- "选择更多"变成了"责任推卸"

v2.0 的思维模式：**不给选择，给流程**
- 用户不需要知道 mode/theme/direction —— 用户只需说"我要什么效果"
- AI 不需要"猜测"用户意图 —— AI 走固定流程提取约束
- 模式从"用户选项"变成"流程中的自动决策"

**核心教训**：Skill 的价值不是暴露更多参数，而是用更少的用户输入做出更好的决策。

### 4.3 从 Visio 集成中学到的 10 条经验

这些不是 spec 里写出来的，是踩坑踩出来的：

1. **用坐标保持布局，不用 Visio 自动布局** —— 自动布局对截图重建不可预测
2. **JSON 是唯一真相源** —— 节点文字、形状、坐标、样式、连接器与渲染脚本分离
3. **决策菱形用真多边形，不旋转矩形** —— 旋转矩形会扭曲文字
4. **手动正交线段替代 Visio 动态连接器** —— 动态连接器会穿过节点或产生意外对角线
5. **先出 .vsdx，再出预览** —— PNG/PDF 导出可能卡死
6. **Windows PowerShell 中文图用 UTF-8 加载** —— `Get-Content -Encoding UTF8 -Raw`
7. **PowerShell 几何函数避免数组返回** —— 返回对象 `{X, Y}`，提前算好标量
8. **Visio 锁定文件时创建新文件名** —— 不要尝试删除或覆盖
9. **首版保守渲染** —— 结构正确后再提升美观
10. **预览是独立 QA 步骤** —— 预览失败但 .vsdx 正常时，交付 .vsdx

**每条经验的共同特征**：来自实际失败，防止特定错误类别，可操作（不是原则而是具体做法）。

## 五、可复用的 Skill 设计模式

### 模式 1：强制执行管线

```
适用场景：任务容易因 AI"自由发挥"而偏离用户预期时

做法：
1. 定义固定步骤顺序
2. 每步有明确的输入/输出
3. 步骤间设置检查点（给用户确认）
4. 不允许跳过步骤
```

### 模式 2：任务分叉 + 互斥路线

```
适用场景：相似的请求对应根本不同的目标时

做法：
1. 识别表面上相似但实质不同的任务类别
2. 定义互斥的执行路线
3. 从用户话中提取关键词判断走哪条
4. 不同路线有不同的验收标准
```

### 模式 3：约束驱动降级

```
适用场景：用户要求与 AI 默认行为冲突时

做法：
1. 定义模式 = {允许, 禁止}
2. 用户约束可以收窄允许集合
3. 冲突时约束优先，模式降级
4. 降级是硬规则，不是"尽量"
```

### 模式 4：中介表示层

```
适用场景：需要从描述生成多种输出时

做法：
1. 定义平台无关的中间格式（JSON）
2. 提取逻辑 → 填充中间格式
3. 渲染器从中间格式生成目标格式
4. 中间格式可被版本控制、审查、diff
```

### 模式 5：禁止事项优先

```
适用场景：AI 的"善意"额外操作恰好是用户最反感的行为时

做法：
1. 收集真实失败案例
2. 归纳为禁止事项清单
3. 禁止事项与允许事项同等篇幅
4. 按模式/路线分别列出
```

### 模式 6：渐进式知识加载

```
适用场景：Skill 知识量大但不同场景需要不同子集时

做法：
1. 主文件包含流程和路由逻辑
2. 深层知识按主题拆分到 references/
3. 主文件告诉 AI"什么情况下读哪个文件"
4. 避免一次性加载所有知识
```

### 模式 7：交付前检查清单

```
适用场景：输出质量有多个维度需要验证时

做法：
1. 定义客观的、yes/no 的检查项
2. 区分结构检查（先）和美学检查（后）
3. 结构不通过不允许进入美学
4. 检查清单写在 skill 指令里，AI 逐项自查
```

## 六、设计原则总结

| # | 原则 | 含义 |
|---|------|------|
| 1 | **提取先于执行** | 不确定就不动手，确认了再画 |
| 2 | **约束高于模式** | 用户说"别动布局"，smart 也降级 |
| 3 | **结构先于样式** | 先正交、对齐、无碰撞，再调色 |
| 4 | **诚实优于完美** | 看不清就说看不清，不编造 |
| 5 | **任务分叉，不混做** | 美化 ≠ 重建，两条路互斥 |
| 6 | **禁止比允许更重要** | 告诉 AI 不做什么比告诉它做什么更有效 |
| 7 | **数据与执行分离** | JSON 描述 what，脚本执行 how |
| 8 | **可检查的验收标准** | 每条标准都是 yes/no，不需要主观判断 |
| 9 | **失败经验驱动改进** | 每条禁止项、每条 lessons learned 都来自真实失败 |
| 10 | **给流程不给参数** | 用户不应该需要理解 mode/theme/direction |

## 七、与 Agent 搭建核心方法论的关联

这个 skill 的构建过程验证了 [[agent-building-guide]] 中的几个关键原则：

- **Skill 是 Harness 层**：SKILL.md 本身就是一个 harness——它不画图，它规定 AI 怎么画图
- **RAG 模式**：references/ 目录本质上是 skill 级别的 RAG——按需检索相关知识
- **Memory 模式**：Lessons Learned 部分本质上是 skill 的长期记忆——从失败中积累
- **Multi-Agent 未使用**：这个 skill 选择用管线而非多 agent，因为流程是顺序的

**反直觉的发现**：最好的 skill 不是暴露最多功能的，而是用最少的用户输入做出最准确决策的。v1.1 的 4×6×5×4=480 种参数组合不如 v2.0 的一句"布局完全一致，做美化"。
