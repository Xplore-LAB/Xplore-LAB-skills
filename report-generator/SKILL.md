# 报告生成器 (Report Generator)

## 这个 skill 解决什么

AI 写报告有两个高频翻车场景：

1. **内容不纯**：报告正文里出现"根据您的要求""我已经为您整理好了""接下来我会分析……"这类元对话痕迹，读者一看就知道是 AI 生成的，不专业。
2. **结构松散**：没有根据报告类型匹配合理的结构骨架，想到哪写到哪，章节之间逻辑断裂，读者抓不住重点。

本 skill 用两条核心原则 + 四步工作流解决这两个问题。

---

## 两条核心原则（比任何格式要求都重要）

### 原则一：干净墙 (Clean Wall)

**报告正文和 AI 的思考/交流必须物理隔离。**

- 报告输出时，正文中**不得出现**任何以下内容：
  - 对用户的回应（"好的，我为您……""根据您的要求……"）
  - 对报告的元描述（"以下是报告正文""接下来是分析部分"）
  - 对读者的喊话（"大家可以看""请注意这一部分"）
  - 不确定性表达（"可能""大概""应该是"——除非是分析结论本身需要保留审慎）
  - AI 身份的暴露（"我整理了""我分析了""建议您"）

- **正确做法**：报告正文就是一份可以直接提交给领导/客户/读者的成品。像正常的报告一样开头、结尾。AI 的确认、追问、说明全部放在报告之外的对话区。

- **为什么重要**：读者看到"根据您的要求"这类话，瞬间出戏，报告的权威感归零。读者不需要知道这份报告是怎么写出来的，只需要知道内容是什么。

### 原则二：结构先行 (Structure First)

**在写任何一个字之前，先确定报告类型和结构骨架。**

- 不同报告类型的结构逻辑完全不同：
  - 工作汇报的核心是"我做了什么 → 结果如何 → 下一步做什么"
  - 调研报告的核心是"为什么调研 → 怎么调研的 → 发现了什么 → 这意味着什么"
  - 技术方案的核心是"要解决什么问题 → 怎么解决 → 为什么这样选 → 怎么落地"

- **正确做法**：先判定报告类型 → 从 `references/` 加载对应结构指南 → 生成大纲 → 用户确认（复杂报告）→ 再填充内容。

- **为什么重要**：结构决定了读者能否快速找到他们关心的信息。结构混乱的报告，内容再好也是废纸。

## 工作流程

### 阶段 0：需求判定 (Intake)

收到用户请求后，先判定四个要素，再进入写作：

| 要素 | 需要确认的内容 |
|------|---------------|
| **报告类型** | 工作汇报 / 项目报告 / 调研分析 / 技术方案？见下方「报告类型速查」 |
| **目标读者** | 给谁看？（直属领导 / 高层 / 客户 / 团队 / 自己存档）决定语言深度和篇幅 |
| **核心信息** | 这份报告最想传达的 1-3 个关键点是什么？ |
| **模板/格式** | 用户是否提供了 .docx 模板？是否有公司固定格式要求？ |

**判定优先级**：
- 如果用户给了 .docx 模板 → 进入**模板填充模式**（见下方）
- 如果用户明确说了报告类型 → 直接加载对应 `references/` 结构指南
- 如果用户没说清楚 → 追问确认，**但不猜**。宁可多问一句，不写错方向。

### 阶段 1：结构规划 (Plan)

1. 根据判定的报告类型，**Read** 对应的 `references/` 文件：
   - 工作汇报/周报/月报 → `references/work-report.md`
   - 项目报告（立项/阶段/结项） → `references/project-report.md`
   - 调研/分析报告 → `references/research-report.md`
   - 技术方案/设计文档 → `references/tech-proposal.md`

2. 结合「目标读者」和「核心信息」，生成**报告大纲**（3 级标题以内）。

3. **确认节点**：
   - 简单报告（周报、简短汇报）：直接进入阶段 2
   - 复杂报告（项目报告、调研报告、技术方案）：**将大纲呈现给用户确认**后再进入阶段 2。确认时只问"这个结构是否合适？有没有需要调整的章节？"，不展开正文。

### 阶段 2：内容生成 (Write)

这是真正写报告正文的阶段。此阶段必须同时遵守两条原则：

**写作规范**：
- 从 `references/style-guide.md` 中取用语言风格、段落结构、数据呈现等通用规范
- 每个章节围绕一个明确的信息点展开
- 段首句给出该段落的核心信息（读者扫读时只看首句就能理解大意）
- 用事实和数据支撑结论，避免空洞的形容词
- 中文报告使用正式但不僵化的书面语

**关键纪律**：此阶段生成的**每句话都必须是报告正文**。如果写了一句"让我们来看看……"或者"我会在下一节介绍……"，立刻删掉重写。报告正文中不出现作者本人。

### 阶段 3：自检交付 (Review & Deliver)

**自检**：交付前，**Read** `references/self-review.md`，逐项检查：

1. **干净墙检查**（最重要）：通读全文，确保没有任何对话痕迹
2. **结构完整性**：是否覆盖了该报告类型的必要章节？
3. **信息密度**：是否有空洞的废话段落？
4. **数据支撑**：结论是否有数据或事实支持？
5. **读者视角**：目标读者能否在 30 秒内抓住核心信息？

**格式输出**：
- 默认输出 **Markdown** 格式（结构清晰、可版本管理）
- 如果用户需要 Word 格式：
  - 有模板 → 先完成 Markdown 定稿，再调用 `template-word-skill` 填入模板
  - 无模板 → 先完成 Markdown 定稿，再用 `template-word-skill` 的从零创建模式生成 .docx
- 本 skill 专注内容和结构，格式转换委托给专门的格式工具

**交付**：给用户的最终消息中，报告正文和简短的交付说明分开。交付说明可以口语化（"报告已生成，共 X 章节，重点突出了 Y 问题"），但报告正文必须干净。

## 报告类型速查

| 类型 | 核心逻辑 | 必含章节 | 典型场景 |
|------|---------|---------|---------|
| **工作汇报** | 做了什么→结果→下一步 | 工作概述、重点进展、数据成果、问题风险、下阶段计划 | 周报、月报、年报、述职 |
| **项目报告** | 项目状态→里程碑→资源→风险 | 项目概述、阶段成果、进度、资源、风险、下一步 | 立项、阶段汇报、结项 |
| **调研分析** | 为什么→怎么做的→发现什么→意味着什么 | 背景目的、方法、现状、发现、对比、结论建议 | 行业调研、竞品分析、技术选型 |
| **技术方案** | 问题→方案→理由→落地 | 背景问题、目标、总体设计、详细设计、选型理由、实施计划 | 系统设计、架构方案、技术选型 |

详细结构指南在 `references/` 对应文件中，按需加载。

---

## 模板填充模式

当用户提供了 .docx 模板文件时：

1. **不要跳过结构规划**。即使是填模板，也要先理解模板的章节逻辑，确保填入的内容与章节匹配。
2. 先用 **Markdown** 完成报告正文（方便检查和修改）。
3. 调用 `template-word-skill`，将 Markdown 内容按模板格式填入。
4. 保留模板的原始格式（字体、字号、页眉页脚等），不修改模板的设计。

如果用户描述了一个模板但没有提供文件（"我们公司的报告模板大概是…"），请用户提供模板文件或详细的章节结构说明。
